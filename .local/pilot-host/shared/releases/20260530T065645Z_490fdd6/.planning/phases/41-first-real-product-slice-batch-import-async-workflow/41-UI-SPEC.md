## Phase 41 visual and interaction contract

This phase extends the existing batch import review surface into an honest async
workflow surface. The visual contract must preserve the current premium K-12
language: Lexend only, tonal layering instead of divider lines, and one batch
detail page as the single truth surface.

### 1. Surface architecture

1. Keep the current batch detail page as the only truth page for review,
   queued, running, retrying, completed, partially completed, and failed states.
2. Keep the course center as a lightweight re-entry point only. It may show the
   latest import task card, but it must always link back to the batch detail
   page.
3. Preserve the existing teacher surface rhythm:
   - page stack: `space-y-6`
   - hero shell: `bg-surface-container-low`, `rounded-[var(--radius-shell)]`
   - inner cards: `bg-surface-container-lowest`, `shadow-ambient`
4. Do not introduce a second task-detail route or operator-style task center in
   this phase.

### 2. Hero and primary action behavior

1. The batch detail hero remains the top anchor for all states.
2. The right-side action inset stays visually distinct with white action-card
   treatment.
3. Before enqueue:
   - headline tone: review-first, action-ready
   - primary CTA: **应用本批导入**
   - helper copy must state that matched rows require review and that actual
     writes happen only after confirmation.
4. After enqueue succeeds:
   - replace “apply” action posture with status-bearing posture
   - primary area must stop implying synchronous completion
   - show durable queued or running truth immediately
5. On dispatch failure:
   - stay on the current batch page
   - show an error-toned status banner near the hero
   - keep the primary CTA available for retry
   - never redirect or show success-toned copy

### 3. Review-state interaction contract

1. Matched rows keep the current two-choice decision model only: **更新** or
   **跳过**.
2. Once a task is successfully created, all row decisions become read-only.
3. Read-only state must be obvious through all three signals:
   - disabled controls
   - reduced emphasis on decision actions
   - explanatory copy: current batch is already processing
4. If an active task already exists for the batch, clicking the CTA must not
   create a second active task. The UI must:
   - reuse the active task
   - keep user on or return user to the same batch page
   - show an informational message: this batch is already being processed

### 4. Async status model and visual mapping

Use one consistent visual mapping across batch detail and recent-task card:

| Async status | Label | Tone | Required UI behavior |
|-------------|-------|------|----------------------|
| `queued` | 排队中 | neutral + accent hint | Show durable task created, waiting to run; never imply success |
| `running` | 导入中 | accent | Show live progress and processed counts |
| `retrying` | 重试中 | accent + warning nuance | Show last attempt failed but system is still working |
| `completed` | 已完成 | tertiary/success | Show summary counts with no failed rows |
| `partially_completed` | 已完成，但有失败项 | mixed success/error | Show both landed work and failed rows honestly |
| `failed` | 导入失败 | error | Show failure reason and re-trigger guidance |
| `dispatch_failed` | 未入队 | error | Local page state only; show queue creation failed before task started |

Rules:

1. Never collapse `partially_completed` into plain completed.
2. Never render `queued` with success color or completion language.
3. Keep domain batch status and async task runtime status visually adjacent but
   conceptually separate.

### 5. Progress and summary contract

1. Top-level information order is fixed:
   - task status / progress
   - aggregate counts
   - row-by-row detail
2. Summary metrics must always show these four result buckets in terminal states:
   `created`, `updated`, `skipped`, `failed`.
3. Running or retrying states must show progress in concrete language, not vague
   loading copy. Preferred structure:
   - processed rows
   - total rows
   - current phase or latest progress note
4. Recent-task card in course center must show one of two payload shapes only:
   - active: status + progress
   - terminal: status + result summary
5. Result summaries must come from durable DTO state, not optimistic client
   inference.

### 6. Partial success contract

1. Partial success headline copy is fixed: **已完成，但有失败项**.
2. The summary cluster must surface both success and failure counts at the same
   time.
3. Failure rows stay visible in the same result page; no modal, no separate tab,
   no inline remediation flow.
4. Failure guidance must point users to correcting CSV data or resolving
   conflicts and then starting a new import attempt.

### 7. Recent import task card contract

1. Place the card near the top information region of the course center, above
   the main course grid or visually attached to the hero metrics.
2. The card must stay lightweight:
   - one title line
   - one status/progress or result line
   - one return-to-batch action
3. Keep the card tonal, not dashboard-heavy:
   - no table
   - no dense logs
   - no operator controls
4. After completion, the card remains visible with the latest summary instead of
   disappearing immediately.

### 8. State-specific UI requirements

#### Queued

- Show a stable queued badge and “task created” confirmation.
- Replace any optimistic success toast with honest queued wording.
- Keep content calm; use skeleton only for unknown sub-data, not for the whole
  page once task id exists.

#### Running

- Show progress prominently above row detail.
- Keep row decision controls frozen.
- Allow navigation away and back without losing state.

#### Retrying

- Show that the system is continuing after a failed attempt.
- Surface latest known failure message in secondary text if available.
- Do not switch to terminal failed posture while retries remain.

#### Completed

- Show clean success headline.
- Show four result counters.
- Keep row-level reasons available below summary.

#### Partially completed

- Use mixed success/error visual cues, but keep success dominant when any work
  landed.
- Show failed count in summary and preserve failure reasons per row.

#### Failed

- Show clear error container at top.
- Explain what failed and what to do next.
- Re-trigger path creates a new task attempt only after terminal failure.

### 9. Component inventory for this phase

Reuse and extend, do not redesign from scratch:

| Area | Component / pattern | Contract |
|------|---------------------|----------|
| Batch detail hero | existing hero shell | Keep as main async truth carrier |
| Primary action inset | white card inset | Switch from CTA-first to status-first after enqueue |
| Summary cards | existing inset cards | Use for batch counts and terminal result counts |
| Status banner | tonal shell / error container | Required for dispatch failure, terminal failed, partial-success guidance |
| Row result cards | existing inset article cards | Preserve row title, badge, reason hierarchy |
| Recent import card | new lightweight hero-adjacent card | Course center only; links back to batch detail |
| Progress placeholder | shadcn `skeleton` | Use only while durable task fields are still loading |

### 10. Motion and feedback

1. Keep motion restrained. Use color and tonal transitions first.
2. State changes may animate with 150ms–200ms transitions only.
3. No celebratory confetti, aggressive pulsing, or long-running shimmer loops.
4. Progress emphasis may animate subtly, but terminal states must settle into a
   static surface.

### 11. Accessibility and input rules

1. All buttons and links must keep 44px minimum target height.
2. Status must never rely on color alone; pair color with explicit label text.
3. Error and partial-success guidance must be readable in plain text without
   interpreting badge color.
4. Focus styles must use the existing primary outline pattern from
   `src/app/globals.css`.

### 12. What this phase must not do visually

1. No generic admin console styling.
2. No divider-line tables as the main result layout.
3. No new global task center.
4. No inline fix-and-rerun UI for individual failed rows.
5. No optimistic “导入成功” message immediately after enqueue.
