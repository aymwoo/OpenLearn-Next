## Component Contract — `lesson-step-editor`

### 1. When the voting editor appears

Render the dedicated voting config section only when all conditions are true:
- `step.type === "quiz"`
- `step.payload.type === "quiz"`
- `step.payload.builtInSource?.builtInKey === "classroomVoting"`

For all other steps, preserve the current editor behavior.

### 2. Layout rule

Stay inside the current left editing column. Insert a single new tonal section titled `课堂投票配置` below `标题` and above `引用材料`.

For classroom voting steps:
- keep the top-level step title field
- replace the generic quiz-only fields with the dedicated voting form
- do not render `正确答案序号`
- do not render `答案说明`
- do not ask the teacher to manage quiz correctness for a voting step

### 3. Voting form fields

Required field order:
1. `投票题目` → maps to executable config `prompt`
2. `投票选项` repeater → maps to executable config `options[]`
3. `参与设置` → `allowMultiple`, `participationWindowSeconds`
4. `结果展示` → `anonymousResults`, `showLiveResults`, `resultsDisplay`
5. `引用材料`

Option repeater rules:
- minimum 2 options, maximum 6 options
- each option row includes label input and remove action
- remove action is disabled when only 2 options remain
- `新增选项` appends a new empty row at the end
- option IDs are invisible to teachers and generated/stabilized by the save layer

### 4. Default-value rule

Hydration priority:
1. Existing valid plugin extension truth for this step
2. `authoringContract.defaultConfig`
3. Never derive defaults from ad-hoc local component constants

On first open with no saved extension truth, show the form already filled from `defaultConfig` and show helper copy:
`已载入课堂投票默认配置，可按本节课需要修改。`

Default config for Phase 56:
- 3 options
- single choice
- anonymous results on
- live results on
- 90-second participation window
- `bar` result display

### 5. Core shell sync rule

The dedicated voting form is the teacher-facing source of truth for classroom voting.

When saving a classroom voting step, the implementation must synchronize the core `quiz` shell in the same save flow:
- `quiz.question` mirrors voting `prompt`
- `quiz.options` mirrors voting option labels in order
- `correctOptionIndex` stays empty / undefined
- `revealCorrectAnswer` stays `false`
- `allowRetry` stays `false`
- `retryPolicy` stays `none`

Teachers must not be asked to edit these mirrored quiz-safety values directly.

### 6. Validation and schema echo

Validation must happen in two layers.

Client-side before save:
- empty `prompt` → inline error under `投票题目`
- fewer than 2 valid options → inline error under option group
- more than 6 options → inline error under option group
- blank option label → row-level inline error
- `participationWindowSeconds` outside `15-600` → inline error under duration field

Server echo after save attempt:
- show returned schema/general save failure in the same voting config section, above the first invalid field group
- do not hide teacher inputs after a failed save
- use destructive color only for actual blocking validation errors

Required blocking copy mapping:
- missing config: `请先填写投票题目和至少 2 个选项。`
- invalid config: `投票配置未通过校验，请按提示修正后重新保存。`
- plugin disabled: `课堂投票插件当前不可用，暂时无法继续发布。`
- incompatible: `课堂投票插件版本不兼容，请刷新页面或联系管理员。`

### 7. Save feedback

Status order inside the step editor:
- idle dirty state: `尚未保存本次修改`
- saving: `正在保存投票配置...`
- success: `投票配置已保存，发布检查已同步刷新。`
- validation error: `配置未通过校验，请先修正红色标记字段。`
- conflict: `检测到更新冲突，请刷新课时后重新应用修改。`
- unknown failure: `保存失败，请稍后重试。`

Presentation rule:
- keep feedback inline in the existing footer status area
- do not open toast-only feedback for critical save outcomes
- success may be duplicated as subtle success text in the voting section, but footer remains canonical

### 8. Preview rule

Keep the existing right-side preview card. For classroom voting steps, preview content must read from the dedicated voting form state:
- title = step title
- description = voting prompt
- support text = `{N} 个选项 · {single/multi} · {window} 秒`
- no correctness language
- no answer explanation copy

## Component Contract — `authoring-status-panel`

### 1. Refresh model

`blockingIssues` must be derived from latest `lesson.publishState.blockingIssues` props, not cached as long-lived local state.

Required behavior:
- after voting config save success, trigger lesson DTO refresh/revalidation
- after refresh, status panel immediately reflects the newest blockers
- when blockers clear, the UI removes them on the next prop update without manual reload
- when new blockers appear, they replace the empty success state on the next prop update

### 2. Publish blocker presentation

Keep the existing `发布准备` card and issue-group structure.

Do not add a new publish blocker page or modal.

For voting-related blockers, each list item must show:
- short label
- explanatory sentence
- step linkage (`step:{id}` or step title if available)
- plugin context when present

Tone rules:
- blocker count badge uses destructive palette only for blockers
- reminder count stays accent/primary tone
- list item surfaces stay tonal; no red outlines or divider lines

### 3. Status copy

Required panel message sequence:
- save initiated elsewhere: `正在保存当前打开的教学环节。`
- save-triggered blocker refresh: `正在刷新发布检查...`
- publish blocked: `发布前检查未通过，请先处理以下阻断项。`
- publish success: `发布成功，学生端将读取最新已发布版本。`

### 4. No stale state rule

The panel must never continue showing a resolved voting blocker after a successful save + refresh cycle.

This is a hard acceptance condition for the phase gap closure.

## Interaction Rules

1. Teacher edits only one source of truth for voting executable config: the dedicated voting section.
2. `保存步骤` saves both mirrored core quiz shell and plugin extension truth in one authored action chain.
3. Successful save is immediately followed by publish-readiness refresh.
4. Failed save never silently clears the form.
5. Publish button state must always match the latest server-derived readiness contract.
6. No visual split between “plugin config editor” and “lesson editor”; voting stays embedded in the lesson editor.

## State Matrix

| State | Trigger | UI response |
|-------|---------|-------------|
| Defaulted | first open, no extension truth | prefill default config + helper copy |
| Dirty | teacher changed any voting field | footer shows unsaved state |
| Saving | save action in flight | disable save CTA, show saving copy |
| Saved | save + refresh succeeded | success copy + blocker list refreshed |
| Client invalid | local schema failure | field-level errors + no save request |
| Server invalid | action returns validation issue | inline section error + footer error |
| Conflict | revision mismatch | conflict copy + require refresh |
| Persisted truth unreadable | bad stored extension/config | fallback to defaults + destructive banner asking re-save |
| Publish blocked | latest readiness has blockers | status panel shows blockers, publish badge shows blocked |
| Publish ready | blockers cleared | status panel empty state + publish enabled |

## Testing Focus

The gap-closure implementation must add or update tests for all items below:

1. classroom voting step renders dedicated voting config section inside `lesson-step-editor`
2. classroom voting step does not render generic correctness fields
3. first-open state hydrates from `authoringContract.defaultConfig`
4. repeated save uses idempotent/upsert semantics and does not duplicate extension truth
5. client validation blocks save for empty prompt / <2 options / invalid window
6. server validation echoes back into the same editor context
7. successful save refreshes publish readiness and clears resolved blocker rows
8. newly introduced blocker appears after refresh without manual reload
9. invalid persisted payload or extension does not crash the entire editor shell
10. publish button enabled/disabled state tracks refreshed server readiness, not stale local state
