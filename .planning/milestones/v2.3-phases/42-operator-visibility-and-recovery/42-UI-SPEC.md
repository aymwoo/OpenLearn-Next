## Phase 42 visual and interaction contract

Phase 42 不是 generic admin console。它是挂在 Settings Labs 下的 operator surface，视觉语言继续遵循 `DESIGN.md`：Lexend、tonal layering、no-line、白色 action card + 浅灰 section shell、克制的 ambient shadow、简体中文界面。

### 1. IA 与页面定位

1. Async operator 固定挂在 `Settings Labs` 下的独立子页，不并入 teacher/staff 产品页，也不并入现有 `runtime-inspector`。
2. 推荐 route 语义为 `/settings/labs/async-tasks` 或等价独立 segment；planner 可微调命名，但不得改变“Settings Labs 独立 operator 子页”定位。
3. Labs 入口必须以单独入口卡片或 quick link 暴露，文案语气为“后台任务运营 / Async Operator / 异步任务排障”一类，不得伪装成教学功能。
4. operator 页面默认只面向 `admin + developer`，但视觉上仍属于同一 OpenLearn 产品宇宙，而不是外接运维台。

### 2. 首页结构：平台健康 + 问题任务

1. 首页第一屏固定回答“平台当前是否健康”。
2. 页面主结构固定为两段：
   - 上半部分：**平台健康**
   - 下半部分：**问题任务**
3. 平台健康区至少包含四类信息：
   - worker connectivity
   - queue health
   - backlog posture
   - degraded status
4. backlog posture 不允许只显示裸数字，必须转译为明确 posture：正常 / 堆积 / 异常，且风险语气先于计数。
5. 若平台处于 degraded posture，顶部必须出现独立告警卡，明确说明：
   - 当前不能信任什么
   - 当前仍可信任什么
   - operator 下一步应去哪里排查
6. 问题任务列表默认按待处理优先级排序，而不是按最近时间倒序。排序优先级固定为：`failed` > `stalled_recovery` > 长时间 `retrying` > 其他需要人工关注状态。
7. 问题任务首页允许使用卡片列表或分组列表；不允许使用 line-heavy dense table 作为主布局。

### 3. 首页视觉节奏

1. 顶部 hero 使用 `bg-surface-container-low` 外层 + `bg-surface-container-lowest` 内层的现有 inspector / settings 语言。
2. 健康指标使用 2-4 个 summary cards；每个卡片只承载一个 posture 主值 + 一条解释，不堆系统日志。
3. 问题任务项必须以摘要卡片呈现，单项至少展示：
   - task label
   - current status
   - latest failure 或风险原因
   - latest progress snapshot 简述
   - 跳转详情入口
4. 卡片之间用留白和 tonal shift 分隔，禁止 1px divider。
5. 页面整体需维持 SETTINGS / inspector 一致的“产品面”气质，不能出现终端式 debug wall 或数据库后台风格。

### 4. 详情页信息层级：摘要优先

1. 单个 task 详情页打开后，用户首先看到的是状态摘要，而不是原始 timeline。
2. 顶部摘要区固定顺序：
   - 当前状态
   - latest error（若存在）
   - recovery posture
   - recent progress snapshot
   - retry eligibility / recovery action
3. `progress snapshot` 必须在顶部摘要区出现，至少包含：
   - progress label
   - `processed / total` 或等价结构
   - 最近更新时间
4. 若任务失败，latest error 必须提升为顶部独立错误卡，不得埋入 attempts 或 timeline 深处。
5. 错误卡文案必须同时回答两件事：
   - 失败发生了什么
   - 现在是否允许 retry / 去哪里继续排查

### 5. Attempt 组织方式

1. attempt history 固定采用“按 attempt 分组”的产品语义，不使用纯事件流作为主视图。
2. 每个 attempt 分组至少要能看见：
   - attempt 编号
   - started posture
   - terminal outcome（failed / completed / partial）
   - 与 recovery event 的关系
3. 当前或最近 attempt 应默认展开；更旧 attempts 可折叠，但不能隐藏存在性。
4. attempt 分组是主分析界面；timeline 只是辅助审计界面。

### 6. Timeline 是辅助审计，不抢主位

1. timeline 只能位于详情页后半段，作为 audit trail 使用。
2. timeline 用于回答“发生过哪些平台事件”，不用于承担“当前应如何判断”这一主任务。
3. timeline item 允许展示 queue / worker / recovery / error 事件，但单项文案保持一句主标题 + 一句说明，避免日志噪音。
4. 不允许把详情页做成“只有时间线，没有摘要卡”的 inspector 克隆版。

### 7. Retry / recovery 交互合同

1. retry CTA 只对 **明确支持 recovery 的 failed task** 展示。
2. `completed`、`partially_completed`、不支持 recovery 的 `failed` task、以及非 terminal active task，都不得显示可执行 retry CTA。
3. retry 采用轻确认模式；可使用 `popover confirm`、`dialog confirm` 或等价模式，但必须在确认前明确说明两件事：
   - 将在同一 durable task 下追加新 attempt
   - 将写入显式 recovery event
4. 不要求 operator 填写长文本说明；确认必须轻量、快速。
5. retry 执行后，页面必须立即回到诚实的 `queued` / `retrying` posture，而不是继续停留在 terminal failed 视觉上。
6. recovery event 必须在详情页可见，且能被 attempts / timeline 追踪到。

### 8. Retry 文案与反馈

1. retry 按钮主文案固定为动词 + 对象：**重试此任务**。
2. 轻确认说明文案固定语义：
   - “这会在当前任务下追加一次新的 attempt”
   - “系统会记录本次 recovery event”
3. 执行成功后的即时反馈使用诚实语气，例如：
   - “已加入恢复流程，正在等待 worker 重新接手。”
4. 不使用“恢复成功”这类提前庆祝文案，直到任务进入真实 terminal success/partial success。

### 9. 状态映射

| Async status / posture | 中文标签 | 视觉语气 | 必须表达 |
|------------------------|----------|----------|----------|
| healthy | 平台健康 | neutral + accent hint | 可以信任当前平台状态 |
| degraded | 平台降级 | warning / error toned | 明确说明哪些能力当前不可靠 |
| queued | 排队中 | neutral + accent hint | 已进入恢复或执行等待，不代表成功 |
| running | 运行中 | accent | 正在处理，显示最近 progress |
| retrying | 重试中 | accent + warning nuance | 前次尝试失败，但系统仍在继续 |
| failed | 执行失败 | error | 必须展示 latest error 与 recovery eligibility |
| stalled_recovery | 恢复中断 | error + warning | 需要人工优先关注 |
| completed | 已完成 | tertiary/success | 可看摘要，不显示 retry |
| partially_completed | 已完成，但有异常项 | mixed success/error | 承认部分落地与异常并存 |

规则：

1. `queued`、`retrying` 绝不使用完成态文案。
2. `failed` 必须伴随显式原因文本，不允许只有红色 badge。
3. `stalled_recovery` 在首页问题任务列表中必须高优先级暴露。

### 10. 组件与布局约束

| 区域 | 组件 / pattern | 合同 |
|------|----------------|------|
| Labs 入口 | settings quick link / entry card | 独立 operator 子页入口 |
| 首页 hero | existing tonal hero shell | 先回答平台健康 |
| 健康概览 | summary cards | posture first, count second |
| degraded 告警 | standalone alert card | 显式说明不可信范围 |
| 问题任务列表 | tonal task cards | 待处理优先，不做 dense table |
| 详情摘要区 | summary shell + white inset cards | 状态、error、progress、recovery CTA |
| attempt history | grouped attempt cards | 主分析界面 |
| timeline | audit cards / event list | 辅助审计，不抢主位 |
| retry confirm | lightweight dialog / popover | 明确追加 attempt + recovery event |

### 11. 交互动效

1. 动效保持克制，以 tonal transition 和 150ms-200ms 状态切换为主。
2. latest error card、degraded alert、selected attempt 可有轻微出现过渡，但不得使用强闪烁、持续脉冲或大面积 loading shimmer。
3. timeline 展开/折叠与 attempt 展开/折叠允许轻量高度过渡；不允许复杂 dashboard animation。

### 12. 可访问性与输入规则

1. 所有状态必须同时由文案和颜色表达，不能只靠 badge 色彩。
2. 错误卡、degraded 卡、retry eligibility 说明必须以可直接朗读的中文句子表达。
3. 焦点样式沿用 `src/app/globals.css` 中现有 primary outline。
4. retry 轻确认必须支持键盘操作与清晰焦点顺序。

### 13. 明确禁止的视觉与交互

1. 不允许 generic admin console / ops dashboard 套皮。
2. 不允许 table-heavy 主布局，尤其是不允许大量 1px 表格线分隔问题任务与 attempts。
3. 不允许把 timeline 放在第一视觉位，迫使 operator 从事件流自己推断当前状态。
4. 不允许把 retry 做成隐式状态切换；必须有显式 recovery action 与 recovery event。
5. 不允许对所有 failed task 一律显示 retry。
6. 不允许把 retry 做成高摩擦长表单审批流。
