## 异步触发时点

### 批量导入的 async task 应该在什么时候真正入队？

| Option | Description | Selected |
|--------|-------------|----------|
| 审核后点应用（推荐） | 保留现有“上传生成草稿 -> 审核命中/阻断 -> 点应用”链路，只把最终 apply 改成异步任务。最贴合当前实现，状态也最好解释。 | ✓ |
| 上传后立刻入队 | CSV 上传完成就直接跑完整导入，减少一步操作，但会把命中已有课程的逐行决策前移或弱化。 | |
| 拆成两段任务 | 上传后先异步做草稿/分析，审核后再异步 apply。能力更强，但复杂度和状态面都会明显上升。 | |

### 当用户在审核页点击“应用本批导入”后，界面应该怎么反馈最符合你的预期？

| Option | Description | Selected |
|--------|-------------|----------|
| 留在当前页并切任务中（推荐） | 点击后立刻显示已排队/运行中的任务状态，当前审核页原地切成“任务进行中”，等结果回来再展示摘要。 | ✓ |
| 跳去独立任务详情页 | 点击后直接跳到专门的 async task 详情页，审核页只做前置配置。 | |
| 回课程中心看状态 | 点击后回到课程中心，在列表或卡片里看任务进度；审核页不再承担运行态。 | |
| 你决定 | 按现有代码和产品一致性来收敛。 | |

### 任务运行期间，这个审核页里的逐行“更新 / 跳过”决策应该怎么处理？

| Option | Description | Selected |
|--------|-------------|----------|
| 入队后锁定决策（推荐） | 一旦任务创建成功，这批 decisions 就冻结，页面改为只读进度与结果，避免运行中再改语义。 | ✓ |
| 允许取消后重改 | 运行中不改，但如果任务支持取消/失败后，可以回到审核态重新选择。 | |
| 始终可改 | 任务运行时也允许继续改 decisions，需要额外处理并发与快照一致性。 | |
| 你决定 | 按最稳妥方案收敛。 | |

### 如果这批导入因为平台层原因连队列都没成功进入，你希望审核页怎么表现？

| Option | Description | Selected |
|--------|-------------|----------|
| 停留审核态并明确失败（推荐） | 不伪装成已开始，页面明确显示 dispatch failed / 未入队，用户可重试触发。 | ✓ |
| 仍切到任务页 | 即使没成功入队，也进入任务视图，由任务状态解释失败。 | |
| 直接 toast 即可 | 只提示失败，不保留明确的失败任务上下文。 | |
| 你决定 | 按 honest posture 收敛。 | |

**User's choice:** 保持现有审核链路，任务在审核后点击应用时创建；任务创建后当前页切为运行/结果页并锁定 decisions；dispatch failed 留在当前页明确失败。
**Notes:** 用户倾向最小改动、最容易解释的产品语义，不希望为了 async 引入第二条页面主链。

| 不要，只在审核页看 | 所有运行态与结果都只留在导入审核页，课程中心不额外暴露。 | |

### 如果用户在课程中心看到这张任务卡，点进去后你希望回到哪里？

| Option | Description | Selected |
|--------|-------------|----------|
| 回该批次导入详情页（推荐） | 无论从审核页还是课程中心进入，最终都回到同一个 batch import 详情/结果页，保持单一事实来源。 | ✓ |

| 你决定 | 按复用和一致性收敛。 | |

**User's choice:** 审核页做主承载面，课程中心补顶部最近导入任务卡片；卡片完成后仍保留最近一次摘要；所有入口回同一个批次详情页。
**Notes:** 用户明确不要为 batch import 再开一套独立任务详情真相页。

## 部分成功怎么表达

### 当一个 batch import 同时出现 created / updated / skipped / failed 时，这个任务的终态你更想怎么命名和理解？

| Option | Description | Selected |
|--------|-------------|----------|
| 单独 partial success（推荐） | 明确它不是纯成功也不是纯失败，任务终态和文案都突出“部分成功 / 仍有失败项待处理”。 | ✓ |
| 归到 completed | 只要任务跑完就算 completed，再在结果摘要里说明有失败项。 | |
| 归到 failed | 只要有任意失败就算 failed，强调需要人工处理。 | |
| 你决定 | 按最诚实、最可解释的语义收敛。 | |

### 任务完成后，详情页最先强调哪一层信息？

| Option | Description | Selected |
|--------|-------------|----------|
| 先看汇总计数（推荐） | 顶部先展示 created / updated / skipped / failed 总览，再往下看逐行明细。适合长批次。 | ✓ |
| 先看失败行 | 一打开先聚焦 failed / blocked 项，摘要次之。 | |
| 先看全部逐行结果 | 把每行结果直接作为主内容，摘要只是辅助。 | |
| 你决定 | 按可读性和教育场景收敛。 | |

### 对于失败行，你希望产品下一步给用户的引导更偏向哪种？

| Option | Description | Selected |
|--------|-------------|----------|
| 明确原因并提示重新导入（推荐） | 逐行保留失败原因，告诉用户修正 CSV 或处理冲突后重新触发新任务，不在当前任务里做行级补救流。 | ✓ |
| 支持当前页就地重试失败行 | 在同一任务结果页里针对失败行补救并再次执行。 | |
| 只展示失败，不给下一步 | 保持最轻实现，用户自己判断怎么处理。 | |
| 你决定 | 按 Phase 41 边界收敛。 | |

### 如果任务处于 partial success，课程中心那张最近导入结果卡片上的主语气应该是什么？

| Option | Description | Selected |
|--------|-------------|----------|
| 已完成，但有失败项（推荐） | 承认任务执行完成，同时明确结果不完整，需要继续处理失败项。 | ✓ |
| 导入失败 | 更强警示，但会掩盖已经成功落库的 created / updated 部分。 | |
| 导入成功 | 更轻，但容易掩盖失败项。 | |
| 你决定 | 按 honest posture 收敛。 | |

**User's choice:** 采用显式 partial success 语义；结果页先看汇总再看逐行；失败行给出原因和重新导入引导；课程中心卡片文案保持“已完成，但有失败项”。
**Notes:** 用户更重视 honest explanation，而不是把 mixed result 压成成功/失败二元标签。

## 幂等与重复触发用户语义

### 如果用户对同一个批次在短时间内重复点击“应用本批导入”，产品应该怎么回应？

| Option | Description | Selected |
|--------|-------------|----------|
| 复用现有进行中任务（推荐） | 如果该批次已有 active task，就返回同一个 task / 详情页，不再新建第二个运行实例。 | ✓ |
| 阻止并报错 | 明确提示“已有任务进行中”，但不自动带用户回已有任务。 | |
| 允许再次新建 | 每次点击都建新任务，但底层靠幂等避免重复写入。 | |
| 你决定 | 按最诚实且最省心的用户语义收敛。 | |

### 这个“同批次已有 active task” 的判断范围，你更希望锁到哪一层？

| Option | Description | Selected |
|--------|-------------|----------|
| 同一 batch 只能有一个 active task（推荐） | 同一个导入批次在 queued / running / retrying 时只能挂一个任务实例，最容易理解。 | ✓ |
| 同一 actor + batch | 只对当前触发人去重，其他人仍可再触发。 | |
| 只靠底层写入幂等 | 产品层不限制，允许多个任务同时存在但结果不重复写。 | |
| 你决定 | 按产品一致性和实现稳定性收敛。 | |

### 如果同一批次的上一次任务已经 completed / partial success / failed，再次点击“应用”时你希望怎样？

| Option | Description | Selected |
|--------|-------------|----------|
| 创建新任务重新跑（推荐） | 已结束任务不复用；用户修正数据或接受再次执行时，创建新的任务尝试，但业务写入仍要防重复污染。 | ✓ |
| 永远复用最后一次任务 | 无论任务结束与否，都只保留一个任务实例。 | |
| 只允许失败后重跑 | 成功或部分成功后不允许再触发。 | |
| 你决定 | 按真实运营场景收敛。 | |

### 当用户点到一个其实已在运行的批次时，页面反馈更像哪种？

| Option | Description | Selected |
|--------|-------------|----------|
| 直接带回现有任务并说明（推荐） | 不要只报错；直接进入该批次详情/运行页，并提示“这批导入已在处理中，已为你打开当前任务”。 | ✓ |
| 只显示不可重复触发提示 | 保留当前页，只告知不能重复。 | |
| 静默无变化 | 按钮不报错也不跳转，尽量减少打扰。 | |
| 你决定 | 按最顺滑的用户路径收敛。 | |

**User's choice:** 同一 batch 只允许一个 active task；重复点击时复用并回到现有任务；terminal 后允许新建新任务重新跑；底层仍要保持业务幂等。
**Notes:** 用户更看重产品面的“找回当前任务”而不是“报错教育用户别点第二次”。
