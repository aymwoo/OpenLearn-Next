<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin form/seed -> Server Action | Untrusted manifest JSON and plugin lifecycle inputs enter server code. |
| Server Action -> Plugin DAL | Validated inputs cross into database mutation/query paths. |
| Plugin DAL -> Action dispatcher | Stored declarative manifest controls whether allowlisted actions can execute. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-01-01 | E/I | `runPluginHook` | mitigate | Treat `schoolId` only as server-derived context, compare with `pluginRegistrations.schoolId`, verify current actor membership/role when actor exists, and deny/audit `school_mismatch` before `dispatchPluginAction`. |
| T-11-01-02 | E | `runPluginHook` permission check | mitigate | Add `PLUGIN_ACTION_PERMISSION_REQUIREMENTS` and deny/audit `permission_denied` when `manifest.permissions` lacks the action requirement. |
| T-11-01-03 | T | `registerPluginManifestAction` | mitigate | Validate `manifestJson` with `PluginManifestSchema` at action boundary; remove `z.any()` as user-facing boundary. |
| T-11-01-04 | R | Plugin audit tables | mitigate | Record failed hook run and action audit for disabled, kill-switch, school mismatch, not allowed, and permission denied. |
| T-11-01-05 | E | Plugin execution model | mitigate | Keep `dispatchPluginAction()` deterministic and allowlisted; no `eval`, remote import, direct DB/API/provider-key path. |
</threat_model>
